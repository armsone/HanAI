# 퍼터 엔진 다중 에이전트 개선 루프

목표는 수치를 임의로 바꾸는 것이 아니라, 한 번의 실험에서 무엇이 좋아졌는지 재현 가능하게 판단하는 것이다. 모든 원본 영상·프레임·오디오는 로컬에서만 처리하고, 공유 산출물에는 정규화 수치·라벨·통계만 남긴다.

## 역할과 단일 작성자

| 역할 | 담당 | 단일 작성 영역 | 산출물 |
| --- | --- | --- | --- |
| 팀장 | Codex | 통합 실행·검증·판정 | 실행 로그, 채택/보류 결정 |
| 알고리즘 | Claude | `apply_putter_engine.py`, `rank_putter_featureprints.swift` | 후보·특징·순위 실험 |
| 데이터 검증 | Gemini | `validate_putter_result.py`, `export_putter_engine_review.py`, 학습 문서 | 분할·누출 감사·검증 보고 |
| 사람 라벨 | 대표님 | 검토 화면 입력만 | 퍼터·퍼터 아님·비샷 라벨 |

에이전트는 같은 파일을 동시에 수정하지 않는다. 각 작업은 다음 단계가 끝난 뒤 파일 경로와 산출물 이름으로 인계한다.

## 한 번의 반복 순서

1. 팀장이 현재 라벨 수, 후보 수, canonical 결과와 worktree를 고정한다.
2. Gemini가 실험용 검증 분할과 평가 기준을 확인한다. replay와 holdout을 섞지 않는다.
3. Claude가 하나의 알고리즘 가설만 구현하거나 실험 파일만 만든다. canonical 결과는 덮어쓰지 않는다.
4. 팀장이 전체 영상을 다시 적용하고 Swift·Python 문법/빌드를 확인한다.
5. Gemini가 1:1 매칭·좁은 허용시간·미라벨 포함 기준으로 결과를 감사한다.
6. 팀장이 채택·보류를 결정하고, 채택한 경우에만 래퍼와 문서에 반영한다.
7. 엔진 상위 후보와 불확실성 후보를 사람에게 제공한다. 사람 라벨은 전용 이력에만 추가한다.
8. 새 라벨이 들어오면 같은 순서로 재실행한다. 단순 상태 보고는 반복으로 세지 않는다.

## 필수 평가 기준

- 주 지표는 `one-to-one`, 후보-라벨 허용시간 1초의 holdout이다.
- replay는 같은 영상 회수 도구로만 보고하고 일반화 성능으로 말하지 않는다.
- 상위 목록의 `unlabeled`는 음성으로 간주하지 않지만, 정밀도 계산에서 제외하지 않는다.
- 후보 하나가 라벨 여러 개를 세거나 라벨 하나가 후보 여러 개를 승인하지 않는다.
- 퍼터 수를 실제 타수로 표현하지 않는다. 현재 자료는 후보-라벨 겹침 검증이다.

## 인계 파일 규약

- `putter-experiment-<name>.json`: canonical을 덮지 않는 실험 결과
- `putter-validation-<name>.json`: 분할·매칭 방식·허용시간을 함께 기록한 검증 결과
- `putter-engine-review-30.json`: replay 상위 후보의 사람 검토 목록
- `putter-engine-label-history.jsonl`: 엔진 후보에 대한 사람의 정정 이력

원본 영상이 필요한 실험은 Claude가 제안하고 팀장이 로컬 실행한다. Gemini는 원본을 받지 않고 정규화 특징과 검증 결과만 검토한다. 검증 실패가 생기면 `문제 인식 → 원인 파악 → 문제 해결 → 원래 업무 재개·완료 확인` 순서로 기록한다.
